Проверил снапшот репозитория из загруженного файла. 

Автоматически прогнал:

* `client`: `npm run check` — прошло.
* `example`: `npm run build` — прошло.
* `server`: `pytest -q` — не прошло, падение уже на collection.

Итоговый вердикт: **как минимум к продакшену и даже к “надежному demo” проект сейчас не провалидирован**. База у него хорошая, но есть несколько блокеров.

Самое критичное:

* **Есть path traversal на сервере через имена узлов.** Для `target_dir` защита есть: `_resolve_target_path()` делает `resolve().relative_to(base_dir)`. Но фактический путь записи в staging строится в `resolve_payload_path()` из сырых `name` без нормализации, а `_handle_file_open()` пишет именно по этому пути. Я локально воспроизвел запись за пределы staging через имя вроде `../../outside.txt`. Это уже security-блокер.

* **Сервер коммитит неполные файлы.** `_handle_session_end()` просто переводит сессию в `COMMITTING`, а `try_commit()` опирается на `count_committed_files()`, который считает все файлы, кроме `rejected/pruned`, и не проверяет, что файл закрыт, что `accepted_offset == final_size`, и что открытых writer’ов не осталось. Я локально воспроизвел сценарий: отправляется половина файла, затем `SESSION_END`, и сервер отвечает `COMMIT_OK`.

* **Заявленная crash-safety расходится с реализацией.** В документации обещано, что после рестарта сервер восстанавливает сессии и клиент делает `RESUME`. Но `recover_session()` действительно восстанавливает даже `COMMITTING`, а `resume()` такие сессии уже запрещает: `cannot resume session in state committing`. Я локально это подтвердил. Значит, часть сессий после падения сервера может застрять навсегда до sweeper’а.

* **Reconnect/resume реализован неполно: metadata-фреймы теряются.** Во время `waiting_resume` `safeWrite()` молча дропает фреймы, а после reconnect `requeuePendingFiles()` умеет переотправлять только файлы. Это значит, что `NODE`/`SUMMARY`/`DIR_CLOSE`, обнаруженные во время дисконнекта или потерянные вместе с неудачным batch POST, не восстанавливаются. На следующем `FILE_OPEN` сервер вполне может ответить `bad_offset`, потому что сам `NODE` он не видел. Это уже не частный баг, а дыра в модели resume.

Что ещё сломано:

* **CI/tests уже красные.** `server/tests/test_protocol.py` импортирует `HashKind`, которого в `server/mfup/protocol.py` нет. Поэтому `pytest` падает ещё до выполнения тестов.

* **Конфигурируемый `MFUP_STAGING_PREFIX` работает неконсистентно.** В `_handle_node()` prefix передаётся в `resolve_payload_path(...)`, а в `_handle_file_open()` — уже нет. Я локально воспроизвел: при нестандартном prefix создаются две staging-директории, а файл уходит в `.incoming.<id>` вместо настроенного префикса.

* **`docker-compose` не самодостаточен для фронта.** `frontend` поднимает `vite`, но `caddy` раздаёт статические файлы из `./example/dist`, смонтированного в `/srv/dist`. То есть после обычного `docker compose up` UI не гарантированно будет доступен, если dist не собран заранее снаружи. 

* **Resume после перезагрузки клиента, похоже, не доведён до конца.** `applyResumeState()` обновляет только уже существующие `trackedFiles`, но они создаются позже в `onDiscover()`. То есть для “нового экземпляра клиента + старый sessionId/resumeToken” принятые offsets не подхватываются нормально. UI-статистика после resume тоже будет неточной: `setFromRootSummary()` восстанавливает байты, но не `acceptedFiles/skippedFiles`, а `setExpiresAt()` вообще не делает `notify()`.

Что бы я чинил первым, по порядку:

1. Жёстко валидировать `node.name` и весь reconstructed payload path, запрещая `..`, `/`, `\` и любые выходы за `payload`.
2. Перед `COMMIT_OK` проверять инварианты: нет открытых writer’ов, все файлы закрыты, `accepted_offset == final_size`, scan sealed.
3. Переделать reconnect/resume так, чтобы переигрывались не только body-файлы, но и все metadata frames, либо чтобы сканирование гарантированно останавливалось до восстановления канала.
4. Согласовать recovery-состояния: `COMMITTING` либо должен автоматически докоммичиваться на старте, либо разрешаться для `RESUME`.
5. Починить тесты и добавить кейсы на traversal, early-commit, resume-after-restart и custom staging prefix.
6. Сделать `docker-compose` реально поднимаемым “с нуля”.

То есть коротко: **frontend собирается, но серверная целостность и безопасность сейчас не проходят валидацию**.
