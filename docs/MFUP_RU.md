# MFUP/2 — протокол потоковой загрузки файлов

## Контекст

Мы разрабатываем WebIDE с пользовательской зоной загрузки кодовой базы. Типичный сценарий: разработчик перетаскивает папку проекта (сотни файлов, от мелких `.ts`/`.json` до больших бандлов) и ожидает, что загрузка начнётся мгновенно и завершится быстро.

Традиционный подход — отправка файлов по одному через `multipart/form-data` POST — оказался неприемлемо медленным. Каждый файл — это отдельный HTTP-запрос: DNS, TLS, заголовки, ожидание ответа. При 188 файлах это 188 последовательных round-trip через океан.

## Проблема

Загрузка папки проекта (188 файлов, 1 МБ суммарно) занимает **17.2 секунды** при file-by-file подходе.

Почему так долго? Размер данных не виноват — 1 МБ пролетит за доли секунды. Виноват **протокол**:

- **188 HTTP-запросов** = 188 round-trip (RTT ~70 мс каждый)
- Каждый запрос: формирование `FormData`, сериализация, отправка заголовков, ожидание `200 OK`
- Запросы **строго последовательные** — браузер не может отправить следующий файл, пока не получит ответ на предыдущий
- Суммарный overhead: ~188 × 70 мс ≈ **13 секунд** только на ожидание ответов

Итого: 95% времени — это не передача данных, а ожидание сети.

## Решение: MFUP/2

MFUP/2 (Multi-File Upload Protocol, version 2) — бинарный потоковый протокол с двумя каналами:

- **WebSocket** — управляющий канал (control): handshake, метаданные, ACK, конфликты
- **HTTP POST** — канал данных (data): непрерывный бинарный поток фреймов

### Ключевые решения

**1. Потоковая передача имён и содержимого в одном потоке**

Вместо "сначала собрать дерево, потом загрузить" MFUP/2 передаёт **одновременно**:

```
NODE(id=1, dir, "src/")  →  NODE(id=2, file, "index.ts")  →  FILE_OPEN(id=2)  →
FILE_CHUNK(id=2, data...)  →  FILE_CLOSE(id=2)  →  NODE(id=3, file, "app.ts")  →  ...
```

Клиент рекурсивно обходит дерево файловой системы и **сразу** отправляет каждый узел — не дожидаясь завершения сканирования. Директории, имена файлов и содержимое чередуются в одном потоке. Это принципиально: браузерный `FileSystem API` отдаёт файлы по мере обхода, и протокол не заставляет буферизировать их в памяти.

**2. Один HTTP POST вместо сотен**

Все 188 файлов передаются в одном `POST /mfup/data/{session}/{leg}` — непрерывный бинарный поток с бинарным кодеком фреймов. Один round-trip на всю загрузку.

**3. Бинарный фреймовый кодек**

Каждый фрейм: `[tag:1][length:4][payload:N]`. Типы: `NODE`, `FILE_OPEN`, `FILE_CHUNK` (с CRC32C), `FILE_CLOSE`, `SESSION_END`. Минимальный overhead — никаких JSON-обёрток для данных.

**4. Конфликты без блокировки**

Если в целевой директории уже есть файлы — сервер отправляет `ASK` через WebSocket. Загрузка **не останавливается**. Пользователь отвечает когда хочет (`merge_overwrite` или `cancel`), ответ применяется при publish.

## Как это работает

```
Клиент                          Сервер
  │                                │
  │──── WS: HELLO ────────────────→│  Handshake + session_id + target_dir
  │←─── WS: HELLO_OK ─────────────│  Epoch, лимиты
  │                                │
  │──── POST /mfup/data ──────────→│  Один непрерывный поток:
  │     [NODE dir "src/"]          │    Сервер создаёт директории
  │     [NODE file "index.ts"]     │    Сервер проверяет конфликты (FSM)
  │     [FILE_OPEN id=2]           │    Сервер открывает файл на запись
  │     [FILE_CHUNK data...]       │    Сервер пишет данные + проверяет CRC32C
  │     [FILE_CLOSE]               │    Сервер закрывает файл
  │     ... ещё 187 файлов ...     │
  │     [SESSION_END]              │    Сервер переходит в COMMITTING
  │                                │
  │←─── WS: FILE_ACK (×N) ────────│  Подтверждения по мере записи
  │←─── WS: COMMIT_OK ────────────│  Все файлы приняты
  │                                │
  │──── POST /publish ────────────→│  Атомарный os.rename() в target_dir
  │←─── { published: [...] } ──────│
```

Весь обмен данными — **2 HTTP-запроса** (один потоковый POST + один publish) и **1 WebSocket** для управления.

## Атомарность: staging → publish

Загрузка и публикация разделены. Пока идёт передача, пользовательские файлы **не появляются** в целевой директории — WebIDE не увидит полузагруженный проект.

### Staging-директория

Все файлы сначала пишутся в изолированную staging-директорию:

```
/data/uploads/.incoming.<session_id>/
  state.sqlite       ← состояние сессии, дерево узлов, прогресс
  payload/
    src/
      index.ts       ← файлы в процессе загрузки
      app.ts
```

Префикс `.incoming` скрывает staging от листинга (точка — скрытый файл) и конфигурируется через `MFUP_STAGING_PREFIX`.

### Двухфазный коммит

1. **COMMITTING** — клиент отправил `SESSION_END`, сервер проверил целостность (CRC32C каждого чанка, `FILE_ACK` для каждого файла). Все файлы записаны в `payload/`.
2. **COMMITTED** → `COMMIT_OK` — сервер подтверждает: данные на диске, сессию можно публиковать.
3. **Publish** — отдельный HTTP POST. Сервер выполняет `os.rename()` (атомарная операция на одной файловой системе) для каждого корневого элемента из `payload/` в `target_dir`.

```python
# Чистый путь — без конфликтов
os.rename("payload/src", "target_dir/src")       # атомарно

# С конфликтами (merge_overwrite)
os.replace("payload/src/index.ts", "target_dir/src/index.ts")  # атомарная перезапись
```

### Гарантии

- **Crash safety**: если сервер упадёт во время загрузки — staging остаётся на диске. При рестарте сервер сканирует `.incoming.*` директории и восстанавливает сессии. Клиент делает `RESUME` и продолжает с последнего `FILE_ACK`.
- **Изоляция**: параллельные загрузки в разные сессии не мешают друг другу — каждая имеет свою staging-директорию и отдельную SQLite базу.
- **Нет частичных результатов**: до вызова publish целевая директория не затронута. Либо все файлы опубликованы, либо ни один.
- **Sweeper**: фоновый процесс чистит протухшие staging-директории по TTL.

## Прогресс-бар: честный и монотонный

Классическая проблема прогресс-баров при загрузке файлов: мы не знаем суммарный размер до завершения сканирования. Если показывать прогресс только по байтам — бар стоит на месте, пока идёт обход дерева. Если только по файлам — бар прыгает при больших файлах.

MFUP/2 решает это **двухфазным blended progress**:

```
fraction = 0.1 × scanFraction + 0.9 × bodyFraction
```

- **scanFraction** (10% веса) — доля просканированных узлов (`scanDone / scanEst`). Растёт по мере обхода дерева файловой системы. Когда сканирование завершено (`sealed = true`), фиксируется на 1.0.
- **bodyFraction** (90% веса) — доля принятых байт (`bodyDone / bodyEst`). Растёт по мере получения `FILE_ACK` от сервера.

Оценки (`scanEst`, `bodyEst`) могут расти по ходу загрузки — например, при входе в глубокую поддиректорию. Чтобы прогресс-бар **никогда не шёл назад**, применяется монотонность:

```
clamped = max(lastFraction, min(1, raw))
```

Эффект для пользователя:
- Прогресс начинает двигаться **сразу** при drop (сканирование даёт первые 10%)
- Основное движение — по мере реальной передачи байт (90%)
- Бар никогда не откатывается, даже если обнаруживаются новые файлы
- При возобновлении (`RESUME_OK`) прогресс восстанавливается из `root_summary` на сервере

## Результаты

Тест: папка проекта, 188 файлов, 1.0 МБ суммарно. Оба бэкенда на одном сервере (сеть одинаковая).

```
┌──────────────────────────────┬──────────────────────────────┐
│   MFUP/2 Protocol            │   Traditional (file-by-file) │
│                              │                              │
│   1.4 sec                    │   17.2 sec                   │
│   ████████████████████ Done  │   ████████████████████ Done  │
│   Files: 188   Sent: 1.0 MB │   Files: 188   Sent: 1.0 MB │
└──────────────────────────────┴──────────────────────────────┘
```

**12× быстрее** при одинаковом объёме данных.

Причём 1.4 секунды — это время работы **обоих бэкендов одновременно**. Традиционный подход стартовал параллельно с MFUP/2, и MFUP/2 завершился ещё до того, как file-by-file успел отправить первые 15 файлов.

### Куда уходит время

| | MFUP/2 | Traditional |
|---|---|---|
| HTTP round-trips | 1 | 188 |
| Сетевой overhead (RTT) | ~70 мс | ~13 000 мс |
| Реальная передача данных | ~1 300 мс | ~1 300 мс |
| Формирование FormData | 0 мс | ~2 900 мс |
| **Итого** | **1.4 сек** | **17.2 сек** |

Передача данных занимает одинаковое время. Разница — в протокольном overhead.

### Масштабирование

Преимущество MFUP/2 растёт с количеством файлов:

- 10 файлов: разница незаметна (~0.7 сек)
- 100 файлов: разница ощутима (~5×)
- 188 файлов: **12× быстрее**
- 1000+ файлов (node_modules): традиционный подход — минуты; MFUP/2 — секунды

Это критично для WebIDE, где пользователь загружает целую кодовую базу и ожидает мгновенной готовности рабочего пространства.
