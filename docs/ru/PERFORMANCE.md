# Производительность и стоимость транспорта

MFUP/3 использует native File/Blob, чтобы не обрабатывать payload в браузерном JavaScript. Дополнительная стоимость относительно обычной загрузки — создание сессии, метаданные receipts, проверка диапазонов, commit и публикация. Возможности этого уровня: продолжение диапазонов, ограниченный обход, группировка запросов и общее разрешение перезаписи.

## Метод измерения

Таблицы относятся к реализации 3.1.0 на 10 сентября 2026: Linux x86_64, AMD EPYC 9654, 12 видимых vCPU, Docker Node 24.20.0/Python 3.12.14, Chromium 151.0.7922.34. Выполнено 66 проверенных измерений: по три повтора на backend, payload и применимый режим. Браузер использует локальный HTTP/1.1 через Caddy без добавленной WAN-задержки. Дисковый cache не очищается. Окружение виртуальное и общее; три повтора не устанавливают статистическую значимость.

Браузер получает реальные дисковые файлы через input. Создание файлов, перечисление picker, загрузка JavaScript и итоговая SHA-256-проверка исключены из времени. После измерения проверяется каждый итоговый файл. Порядок режимов ротируется. MFUP использует шесть запросов, 128 частей, корзины 32 МиБ, диапазоны 16 МиБ и окно 8 мс, без прикладных hooks обработки/маппинга и конфликтов назначения.

- Общее время — от создания сессии/запроса до опубликованных файлов; для MFUP включает connect, upload, commit, publish.
- Backend CPU — user+system процесса приёма, включая рабочие потоки Node. Это не CPU всей машины; Caddy и прочие процессы исключены.
- Главный поток — Chromium Performance.TaskDuration за операцию, а не CPU всего браузера или native чтения/сети.
- Размеры сети — тела HTTP и байты JSON-сообщений WebSocket. HTTP headers, WebSocket framing/handshake, TCP/IP не включены. Это не счётчики интерфейса сети.

Тривиальный FormData добавляет весь список и выполняет один fetch. Пофайловый вариант использует шесть workers и отдельный FormData на файл. Raw File — одно тело запроса, только для одиночных файлов. Базовые варианты сохраняют файлы без постоянной сессии, разрешения и продолжения диапазонов. Node использует потоковую запись Busboy. Обычный Python request.form/UploadFile сначала сохраняет большой файл временно, затем копирует в назначение; MFUP пишет диапазоны напрямую. Разница включает реализацию приёмника и дисковый I/O, а не только обрамление протокола.

Списки в измерениях плоские. Папочный input браузера может передать относительные пути обычному FormData; само дерево файлов не требует MFUP. Пустые каталоги требуют отдельных метаданных, поскольку отсутствуют в FileList.

Большой файл выигрывает от native сериализации браузера и прямой записи диапазонов. Маленькая загрузка платит за сессию и управление. Для множества малых файлов один FormData может быть быстрее за счёт отсутствия журнала диапазонов и плана публикации. Это локальные измерения, а не гарантии для других дисков, устройств и сетей.

Границы и заголовки multipart растут с числом частей. MFUP добавляет tuple манифеста на диапазон, JSON сессии, receipts и снимки. Опубликованный снимок содержит до 256 путей, счётчик и курсор. Resume проверяет только диапазоны текущей корзины булевым списком, без полного индекса сессии. Новая загрузка не требует дополнительного status-запроса. Общий управляющий трафик пропорционален диапазонам операции, но отдельный ответ ограничен.

При лимите 128 частей планировщик группирует 1 000 малых файлов в восемь data-корзин; create, commit, publish добавляют три запроса управления. Файл 64 МиБ использует четыре диапазона по 16 МиБ. Распределение диапазонов по корзинам зависит от готовых элементов и лимитов.

## Задержки, память и работа приложения

Относительно одного обычного POST create, commit, publish добавляют три последовательных обмена при клиентской публикации. При RTT 50 мс только эта зависимость может добавить около 150 мс до обработки и окна сбора. Это расчёт зависимостей, а не WAN-замер. Предварительное подключение скрывает задержку создания; server autoPublish может убрать отдельный клиентский publish.

Шесть запросов делят полосу соединения и канала. HTTP/2 может объединить их в одно соединение; потери TCP влияют на все потоки. Сам multipart не даёт продолжения диапазонов. После прерывания MFUP проверяет receipt и повторяет только неподтверждённое; проверка добавляет запрос управления, потерянная корзина может стоить повторной передачи своего неподтверждённого payload.

SDK удерживает до 10000 ожидающих записей вместе с активными корзинами и продолжает обход при 5000. Подтверждённые ссылки освобождаются; полного набора entries и индекса resume в памяти нет. Native FileList и страницы перечисления принадлежат браузеру; SDK не дублирует FileList. Drop допускает до 10000 выбранных корней, содержимое которых читается постепенно. Payload остаётся в native File/Blob. Постоянные метаданные и индексы занимают O(files+ranges) на диске. Проверки путей используют индексные запросы на каждый префикс и ограниченную корзину новых назначений. Снимки используют сохраняемые счётчики. Commit и публикация обходят страницы по 256 записей; метаданные манифеста и receipt сохраняются транзакциями на корзину. Mapper добавляет задержку callback до чтения тела корзины и позволяет рано задать вопрос. Чтение содержимого в onCommitted добавляет прикладной I/O. Дополнительного прохода по payload и внешнего сервиса хранения нет. Демо показывает страницы по 256 опубликованных файлов; получение отсортированной страницы сканирует каталог с ограниченной памятью.

Перезапись использует один флаг конфликта и один флаг разрешения. Первый конфликт и первое разрешение требуют по одному обновлению сессии. Согласие — один POST с {"overwrite":true}: 18 JSON-байтов до HTTP-обрамления. Вопрос и первая ошибка имеют постоянный размер по числу конфликтов; страница путей ограничена 256 элементами. Дополнительного прохода payload или отдельного сервиса хранения нет.

XHR-уведомления объединяются каждые 50 мс, используют native upload events и не создают polling-канал. Они оценивают активный payload, не подтверждая запись. После прерывания оценка может уменьшиться. Измеренный режим использует fetch; время прикладного XHR-рендеринга, конфликтов, физических устройств, peak RSS и восстановления после потери питания этими таблицами не подтверждается.
