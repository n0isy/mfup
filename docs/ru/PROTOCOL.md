# HTTP-протокол MFUP/3

Файлы передаются через обычный `multipart/form-data`. Управление сессией использует JSON HTTP. WebSocket передаёт уведомления о состоянии. Все пути ниже относительны к настроенному префиксу адаптера.

## Endpoints

| Метод и путь                            | Вход                                                                | Результат                                 |
| --------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------- |
| GET `/mfup/health`                      | Нет                                                                 | `protocol`, `backend`                     |
| POST `/mfup/sessions`                   | `protocol: "MFUP/3"`, опциональные `targetDir`, `meta`, `overwrite` | `id`, `token`, `epoch`, `limits`          |
| GET `/mfup/sessions/:id`                | Bearer token                                                        | Снимок сервера                            |
| POST `.../:id/resume`                   | `{}`                                                                | Новый epoch, снимок и лимиты              |
| GET `.../:id/files?after=...&limit=256` | Курсор пути                                                         | Файлы с принятыми offsets и курсор `next` |
| POST `.../:id/batches/:batchId`         | Multipart; `X-MFUP-Epoch`                                           | Receipt: `id`, `parts`, `bytes`           |
| GET `.../:id/batches/:batchId`          | Нет                                                                 | Сохранённый receipt или 404               |
| POST `.../:id/commit`                   | `files`, `dirs`, `bytes`                                            | Снимок committed или published            |
| POST `.../:id/properties`               | `overwrite: boolean`                                                | Снимок                                    |
| POST `.../:id/answers`                  | `id: "overwrite"`, `choice: "overwrite"` либо `"cancel"`            | Снимок                                    |
| POST `.../:id/publish`                  | `{}`                                                                | Снимок                                    |
| POST `.../:id/cancel`                   | `{}`                                                                | Cancelled либо уже published              |

Endpoints с ID сессии требуют `Authorization: Bearer <token>`. Прикладная авторизация вызывается при создании. Значения по умолчанию: `targetDir` — uploads, `meta` — null, `overwrite` — false. Произвольные переменные приложения находятся в `meta`, включая поле `scope`. Значения и вложенность JSON сохраняются для авторизации, обработки и маппинга. Они не становятся настройками протокола.

Результаты авторизации, назначение, метаданные и context сохраняются. Resume продолжает существующую сессию, не повторяет авторизацию и не заменяет метаданные. Пределы UTF-8 JSON: 16 КиБ для meta, 64 КиБ для серверного context, 256 КиБ для тела HTTP-управления. Context и абсолютные корни не передаются браузеру.

## Multipart-корзина

Первая часть — текстовое поле `manifest`:

```json
{
  "files": [
    ["photos/a.jpg", 1000, 1750000000000, 0, 1000],
    ["photos/b.jpg", 30000000, 1750000000000, 16777216, 13222784]
  ],
  "dirs": ["photos", "empty-directory"]
}
```

Кортеж файла: `[path, fullSize, mtimeMs, offset, length]`. Части файлов следуют в порядке кортежей с именами `0`, `1` и далее. Multipart filename не задаёт назначение. Boundary выбирает браузер; нельзя самостоятельно задавать Content-Type без boundary.

```js
const body = new FormData();
body.append("manifest", JSON.stringify(manifest));
body.append("0", fileA, fileA.name);
body.append("1", fileB.slice(16777216), fileB.name);
```

Manifest ограничен 256 КиБ. Части файлов и записи каталогов учитываются в maxParts. По умолчанию: concurrency 6, maxParts 128, batchBytes 33554432, partBytes 16777216. Offset кратен partBytes; length равен минимуму partBytes и остатка файла. Пустой файл имеет один диапазон нулевой длины с offset 0. Параллельные диапазоны не пересекаются.

Сервер проверяет порядок, размеры и закрывающий boundary, записывает payload и фиксирует диапазоны перед receipt. Batch ID обозначает неизменную операцию. Повтор с другим manifest даёт 409. Сохранённый receipt не заменяет уже принятые байты. После потери ответа нужно проверить receipt перед повторной отправкой.

Счётчики и offsets протокола — неотрицательные безопасные целые JavaScript. Пути относительные, с `/`, нормализуются в NFC, ограничены 1024 UTF-8 байтами и 240 байтами на сегмент. Имена и префиксы, различающиеся только регистром, не сосуществуют в сессии. Правила путей не применяются к произвольным строкам meta. Общее число файлов и каталогов ограничено `4 * maxFiles + 1024`.

## Состояние и уведомления

Состояние сервера: `uploading -> committed -> publishing -> published` либо cancelled. Commit требует все диапазоны и совпадение числа файлов, каталогов и байтов. Повтор успешного commit возвращает текущее состояние без повторной прикладной обработки.

Снимок содержит `id`, `epoch`, `state`, `files`, `bytes`, `asks`, `published`, `overwrite`, `overwriteRequired`, `error`, `clientPublish`, `processing`. Processing: none, pending, running, done, failed. Ошибка hook обработки оставляет принятые файлы committed и сообщает `processing: "failed"`; принятый commit не становится неудачной загрузкой.

Клиент открывает `/mfup/control` и за пять секунд отправляет `{ "type": "subscribe", "id": "...", "token": "..." }`. Сервер передаёт полные снимки. SDK переподключает control socket после разрыва; HTTP GET также возвращает текущее состояние. WebSocket не передаёт файлы или изменяющие состояние ответы.

Resume дожидается допущенных запросов и увеличивает epoch. Новые data requests передают актуальный epoch. Сервер ограничивает параллелизм независимо от планировщика клиента. Страница файлов содержит не более 256 записей; offsets большого файла могут занимать длинный список. Метаданные пропорциональны числу файлов и диапазонов.

Ticket даёт доступ к одной сессии. После перезагрузки браузера пользователь повторно выбирает источник; сопоставление выполняется по пути, размеру и mtime. Принятые диапазоны не отправляются повторно. Пауза прерывает активные клиентские запросы и не является конечным состоянием сервера. HTTP-управление по умолчанию имеет срок ожидания 30 секунд (`requestTimeoutMs`); длинные data POST этим сроком не ограничены.

SDK по умолчанию делает до трёх допустимых повторов передачи с задержками 100/200/400 мс и проверкой receipt. Бесконечные повторы при отсутствии сети не гарантируются. Неподтверждённые байты могут потребовать повторной отправки. Результаты публикации доступны до TTL сессии, по умолчанию 24 часа с продлением операциями. 404 после истечения срока не доказывает результат прежней публикации.

## Перезапись и отмена

Перезапись — одно сохраняемое разрешение сессии. Первый конфликт выставляет `overwriteRequired: true`; приём может продолжаться. Приложение показывает один опциональный вопрос на загрузку. `POST properties {"overwrite":true}` разрешает все текущие и будущие конфликты. Разрешение записывается до подтверждения и сохраняется при resume/restart. Повтор true идемпотентен; true обратно в false даёт `409 overwrite_already_approved`.

`asks` пуст или содержит один элемент:

```json
{
  "id": "overwrite",
  "message": "overwrite_required",
  "choices": ["overwrite", "cancel"],
  "answer": null
}
```

После разрешения, отмены или публикации вопроса нет. Пофайлового skip нет. Endpoint answers выполняет те же действия для всей сессии.

| Решение   | Во время передачи                                                                              | После commit, до публикации                                    |
| --------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Разрешить | Сохранить разрешение, продолжить приём без вопросов; существующие файлы остаются до публикации | Публикация продолжается согласно клиентской/серверной политике |
| Отменить  | Сохранить cancelled, остановить запросы, исключить поздние receipts/публикацию                 | Удалить staging, сохранить существующие назначения             |

Отмена идемпотентна и упорядочена с публикацией. После завершения публикации cancel возвращает published. Отмена во время callback исключает позднюю публикацию; очистка staging дожидается callbacks. Ошибка очистки не отменяет cancelled, sweeper может повторить удаление. Уже заменённые при частичной публикации файлы не восстанавливаются.

SDK показывает cancelling до ответа или снимка с подтверждением. Если подтверждение получить не удалось, сообщает о неподтверждённой отмене и допускает повтор. Поздние ответы не меняют уже подтверждённые cancelled/published.

## Публикация и сохранность

По умолчанию SDK autoPublish=true, сервер autoPublish=false, сервер clientPublish=true. При clientPublish=false HTTP publish даёт `403 server_publish_only`; доверенный backend может публиковать. Незавершённая или неудачная обработка блокирует клиентскую публикацию с `409 processing_required`. Server autoPublish может публиковать во время commit или после разрешения перезаписи. Разрешение не обходит полноту commit.

Маппинг выполняется после commit. Проверенный полный план сохраняется до перемещений и используется при повторах/restart. Отсутствующий принятый файл до публикации — операционная ошибка, а не доказательство правильности старого назначения. Rename файла атомарен; публикация дерева не является одной транзакцией и не откатывает заменённые файлы. Приложение не должно менять назначения незавершённой публикации.

SQLite/WAL и корни сессий имеют одного владельца-процесс. partBytes закреплён за каталогом метаданных. Receipts сохраняются после перезапуска; fsync payload для гарантий при потере питания не выполняется. Прикладная обработка и расположение данных описаны в [контракте расширения](EXTENDING.md).

## Ошибки

Операционные ответы содержат error, message, retryable и phase:

```json
{
  "error": "storage_full",
  "message": "Server storage is full",
  "retryable": false,
  "phase": "upload"
}
```

Поведение приложения определяется кодом, а не текстом message, который может отличаться между адаптерами. Исходные исключения и абсолютные пути остаются в диагностике сервера.

| HTTP | Примеры кодов                                                                                                                                       |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400  | bad_manifest, bad_range, bad_path, bad_property, part_size_mismatch, incomplete_multipart                                                           |
| 403  | denied, server_publish_only                                                                                                                         |
| 404  | not_found, unknown_question                                                                                                                         |
| 408  | request_timeout                                                                                                                                     |
| 409  | stale_epoch, file_changed, batch_conflict, range_busy, answers_required, incomplete, mapping_error, processing_required, overwrite_already_approved |
| 413  | batch_too_large, body_too_large, quota_exceeded, meta_too_large                                                                                     |
| 429  | busy                                                                                                                                                |
| 500  | server_error                                                                                                                                        |
| 503  | storage_unavailable                                                                                                                                 |
| 507  | storage_full                                                                                                                                        |

ENOSPC, EDQUOT, SQLite FULL соответствуют storage_full. Ошибки чтения/записи/открытия, например EIO, EROFS, EACCES, соответствуют storage_unavailable. Они не обозначаются как неправильный multipart. Неудачная корзина не получает receipt; слот запроса освобождается даже при ошибке close/flush.

Первый операционный отказ записывается в snapshot.error как `{code,status,phase,retryable}` и доступен SDK через errorInfo. Если SQLite не может сохранить его, используется доступное состояние процесса; недоступная БД не обеспечивает сохранность. Resume или явная публикация очищает прежнюю ошибку при доступном хранилище. retryable=false исключает автоматическую повторную отправку тела; явный повтор возможен после устранения причины. UI показывает одну ошибку загрузки вместо ошибок каждого прерванного запроса.

## Счётчики байтов клиента

confirmedBytes учитывает payload с receipts. При trackUploadProgress=true события XHR оценивают активный payload для sentBytes; уведомления объединяются каждые 50 мс. Пользовательский fetch имеет приоритет и не даёт XHR events. Из-за multipart headers/boundaries sentBytes — оценка, а не счётчик сетевого интерфейса или подтверждение хранения. Прерванные оценки удаляются; полоса может двигаться назад. Demo показывает максимум 99% до published, в том числе когда все байты отправлены, но ожидается разрешение.
